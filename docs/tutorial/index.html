Этот учебник объясняет не только «что лежит в какой папке», а причинно-следственную цепочку: какое требование решает каждая технология, где обеспечивается гарантия и каким тестом это доказано. Переключайте уровень объяснения слева.

0. Как проходить учебник

После курса вы сможете проследить покупку от двойного клика до кода, объяснить идемпотентность, inbox, очередь PostgreSQL, безопасный retry и найти реализацию каждого механизма по прямой ссылке.
  1. Сначала прочитайте архитектуру и пройдите путь одной покупки.
  2. Затем разберите три главные гонки: двойной клик, повтор webhook, timeout поставщика.
  3. Открывайте ссылки «код» рядом с объяснениями и сопоставляйте текст с реализацией.
  4. После каждого модуля отвечайте вслух, а затем раскрывайте правильный ответ.
  5. В конце пройдите итоговый тест и повторите разделы, где ответили неверно.
Комментарии добавлены в исполняемые TypeScript-файлы, Angular-шаблоны, Prisma/SQL, Docker и CI. В JSON, lock-файлы и сгенерированные артефакты комментарии намеренно не вставлены: JSON их не поддерживает, а generated-файлы должны пересоздаваться генератором.

1. Архитектура: путь одной покупки

Angular→NestJS API→PostgreSQL→Webhook inbox→Worker→Provider A/B→Код покупателю

Профессионально

Система разделяет синхронный HTTP-контур и асинхронную обработку. API быстро валидирует запрос и атомарно фиксирует намерение в PostgreSQL. Webhook сначала попадает в durable inbox, после чего worker в отдельных коротких транзакциях меняет state machine заказа и создаёт delivery job. Внешний вызов поставщика выполняется вне транзакции. Финальная запись fulfillment снова защищена блокировкой строки и UNIQUE.

Как для 10 лет

Представь ресторан. Официант записывает заказ в тетрадь и сразу говорит «принято». Повар потом берёт карточку, готовит блюдо и отмечает результат. Даже если посетитель дважды крикнул заказ или официант дважды принёс записку, в тетради остаётся одна покупка и выдаётся один ключ.

Почему не один большой HTTP-запрос?

Платёж и поставщик — внешние системы: они могут отвечать медленно, повторять сообщения или оборвать соединение после выполнения операции. Если держать всё в одном запросе и одной транзакции, блокировки станут длинными, а падение процесса потеряет промежуточное состояние. Запись этапов в БД делает процесс продолжимым.

Контрольный вопрос: зачем API и worker разделены?

API быстро принимает запросы, а worker надёжно повторяет длительную обработку. Падение worker не мешает принимать webhook: события уже сохранены в PostgreSQL.

Профессионально

Prisma выбран для CRUD и типизации, но не скрывает специфические возможности БД. Там, где correctness зависит от уровня блокировок, используется параметризованный raw SQL. Это прагматичная граница: ORM повышает скорость разработки, PostgreSQL остаётся источником строгих инвариантов.

Как для 10 лет

Angular рисует магазин, NestJS разговаривает с браузером, PostgreSQL хранит тетрадь, Prisma помогает удобно в ней писать, а Docker выдаёт всем одинаковую коробку с нужными деталями.

Контрольный вопрос: почему одной проверки TypeScript недостаточно?

Типы не координируют два одновременно работающих процесса. Гонки останавливают транзакции, блокировки и ограничения UNIQUE непосредственно в общей базе.

Профессионально

Как для 10 лет

Это один большой конструктор с отдельными коробками. Детали экрана лежат в web, детали разговора — в api, ночной помощник — в worker, а общие правила лежат в коробке domain, чтобы их не копировать.

Контрольный вопрос: зачем правила цены вынесены из контроллера?

Чтобы HTTP-слой только переводил запросы, а бизнес-правило было единым, независимо тестировалось и могло одинаково использоваться разными приложениями.

4. Домен: статусы, деньги и неизменяемые правила

Домен — это язык задачи. Здесь нет кнопок и HTTP: только разрешённые статусы, переходы, вычисление цены и отпечаток заказа.

created→paid→delivering→delivered

Ответвления ошибок: created → payment_failed, delivering → out_of_stock или delivery_failed. Восстановление разрешает вернуть ошибку выдачи в delivering. После delivered регресс запрещён.

Профессионально

State machine централизует допустимые переходы и исключает случайные присваивания. Цена хранится целым числом копеек: это исключает двоичные ошибки floating point. fingerprintOrder канонизирует значимые поля intent; его сравнение отличает корректный replay от переиспользования ключа с другим телом.

Критические гарантии продублированы в БД: fulfillments.order_id UNIQUE, fulfillments.code UNIQUE, payment_events.event_id UNIQUE. Код проверяет намерение, БД остаётся последней линией защиты.

Как для 10 лет

У заказа есть клетки настольной игры. Фишку можно двигать только по нарисованным стрелкам. Если ключ уже отдан, назад фишку двигать нельзя. Деньги считают копейками, как целыми кубиками: половинка случайно не потеряется.

Код: расчёт цены, fingerprint заказа, модель Order.

Контрольный вопрос: почему цена — не число 19.99?

Десятичные дроби часто нельзя точно представить в двоичной памяти. Значение 1999 копеек целое, поэтому сумма, скидка и сравнение выполняются предсказуемо.

Контрольный вопрос: почему правил в TypeScript и UNIQUE в БД не слишком много?

Они решают разные задачи. Код сообщает понятную бизнес-ошибку, а UNIQUE гарантирует корректность даже в гонке между двумя процессами.

5. Создание заказа и идемпотентность двойного клика

POST /api/v1/orders
Idempotency-Key: один-стабильный-ключ
{ "orderId": "публичный-uuid", "sku": "steam-1000", "promoCode": "START10" }

Профессионально

Клиент генерирует UUID intent и один idempotency key до запроса. API загружает товар и цену исключительно с сервера, блокирует строку промокода при необходимости, создаёт redemption и заказ в одной транзакции. Уникальность orders.idempotency_key сериализует гонку без глобальной блокировки.

При конфликте P2002 проигравший запрос читает победившую запись. Если fingerprint совпал — возвращается прежний заказ с HTTP 200; если содержимое иное — HTTP 409. Так retry безопасен, но ключ нельзя использовать для другой покупки.

Как для 10 лет

Покупатель приклеивает к покупке уникальный номер. Если кнопка нажалась дважды, продавец видит тот же номер и отвечает: «Этот заказ уже записан». Если с тем же номером пытаются заказать другой товар, продавец замечает подмену и отказывает.

Клиент не присылает сумму, которой можно доверять. Даже если изменить JavaScript в браузере, API берёт цену из products, применяет скидку сам и сохраняет snapshot цены в заказе.

Код: Angular buy(), ShopService.createOrder().

Контрольный вопрос: можно ли генерировать новый key при каждом retry?

Нет. Сервер воспримет его как новое намерение и сможет создать второй заказ. Один пользовательский intent должен жить с одним ключом до однозначного ответа.

6. Платёжный webhook и durable inbox

Платёжная система→payment_events: pending→HTTP 200→worker применяет событие

Профессионально

Endpoint сначала атомарно вставляет событие в inbox и только затем отвечает 200. event_id UNIQUE делает повтор доставки безопасным. Внешний UUID заказа намеренно не является обязательным FK события: webhook может прийти раньше создания заказа и остаться pending.

Worker позже блокирует событие, ищет заказ и проверяет сумму с валютой по snapshot. Валидный paid имеет приоритет над failed, а delivered никогда не регрессирует. Пятьдесят разных paid-событий могут храниться для аудита, но unique delivery job запускает выдачу лишь однажды.

Как для 10 лет

Почтальон может принести одно письмо дважды или письмо может приехать раньше посылки. Мы сначала кладём письмо в надёжный ящик и ставим на нём номер. Повторное письмо с тем же номером не считается новым, а раннее спокойно ждёт появления заказа.

Код: приём webhook, применение события worker, PaymentEvent.

Контрольный вопрос: почему нельзя сначала ответить 200, а потом сохранить?

Процесс может упасть между ответом и записью. Платёжная система уже считает доставку успешной и не повторит webhook — оплаченный заказ будет потерян.

Контрольный вопрос: что происходит с webhook до заказа?

Он сохраняется со статусом pending. Worker не помечает его применённым и вернётся к нему после появления соответствующего публичного orderId.

7. Worker и очередь в PostgreSQL

SELECT id
FROM delivery_jobs
WHERE status = 'pending' AND run_after <= now()
FOR UPDATE SKIP LOCKED
LIMIT 1;

Профессионально

Несколько worker могут одновременно claim-ить задания. SKIP LOCKED пропускает уже занятые строки вместо ожидания. Claim — короткая транзакция: статус переводится в processing, записывается lease owner/expiration, затем lock освобождается. HTTP поставщику выполняется уже вне транзакции.

Lease позволяет вернуть зависшее задание после падения процесса. run_after задаёт backoff, attempts ограничивает безопасные повторы. Финализация снова блокирует заказ и проверяет его состояние, поэтому устаревший worker не перезапишет более новый результат.

Как для 10 лет

На столе лежат карточки заданий. Каждый помощник быстро ставит на одной карточке своё имя и уносит её. Занятые карточки другие не ждут, а берут следующую. Если помощник пропал, срок подписи закончится и карточку можно будет подобрать снова.

Код: claim и processDeliveryJob(), DeliveryJob.

Контрольный вопрос: почему HTTP нельзя выполнять внутри транзакции?

Неизвестно, сколько ответит сеть. Длинная транзакция удерживает locks, увеличивает конкуренцию и риск дедлоков. В БД фиксируется намерение, HTTP идёт без lock, затем результат атомарно финализируется.

8. Поставщики: самая опасная ловушка timeout-after-issue

стабильный request_id→Provider A резервирует код→ответ потерян→повтор того же request_id→тот же код

Профессионально

Timeout не доказывает, что операция не состоялась. Поэтому для пары заказ/поставщик создаётся стабильный provider_request.request_id. Mock-provider сначала атомарно резервирует key и записывает request_id → code, а уже после может имитировать потерю ответа. Replay возвращает прежний результат и не расходует новый ключ.

После timeout/5xx worker повторяет A с тем же ID. На B разрешено переключиться только после однозначного out-of-stock от A: лишь тогда доказано, что A ничего не выдал. Если A молчит после возможной выдачи, fallback мог бы выдать второй товар.

Как для 10 лет

Ты попросил кладовщика выдать билет, но телефон оборвался. Нельзя сразу звонить другому кладовщику: первый мог уже отдать билет. Надо повторить первому тот же номер просьбы. Он посмотрит запись и вернёт именно прежний билет.

Код: callProvider(), ProviderService.issue(), атомарная complete().

Контрольный вопрос: можно ли после timeout A сразу вызвать B?

Нет. Timeout — неопределённый исход: A мог выдать код. Сначала повторяем A с тем же request_id. B допустим лишь после явного ответа A «ничего не выдано / нет остатков».

Контрольный вопрос: где физически предотвращается второй fulfillment?

В транзакции complete проверяется текущий заказ, а в таблице действует order_id UNIQUE. Отдельный code UNIQUE не позволяет закрепить один код за двумя заказами.

9. Промокоды под конкурентной нагрузкой

Профессионально

Строка промокода читается FOR UPDATE внутри транзакции создания заказа. После проверки активности и лимита создаётся уникальный redemption для заказа и увеличивается used_count. Параллельные запросы сериализуются на одной строке, поэтому успешных применений не больше max_uses.

Повтор того же idempotency key не создаёт новый redemption: проигравшая транзакция откатывается полностью, а запрос получает уже созданный заказ.

Как для 10 лет

У кассира осталось три купона. К каждому подходит только один человек за раз, кассир ставит галочку и уменьшает остаток. Даже если одновременно прибежали 50 человек, четвёртого купона из воздуха не появится.

Код: транзакция заказа и промокода, Promocode и PromoRedemption.

Контрольный вопрос: почему недостаточно сначала прочитать used_count, затем обновить?

Два запроса могут одновременно увидеть одно и то же старое значение и оба пройти проверку. Блокировка строки превращает проверку и увеличение в одну последовательную критическую секцию.

10. Angular: три экрана и пользовательский путь

Маршрут Компонент Ответственность
/ StorefrontComponent Каталог, карусель, меню, Steam, покупка
/orders/:orderId OrderComponent Статус, симуляция оплаты, история, код

Профессионально

Standalone components загружаются лениво через router. HttpClient получает серверный каталог, signals хранят локальное состояние. Storefront удерживает idempotency intent между повторами одной покупки. Order использует polling RxJS, пока заказ не достиг терминального состояния. Admin добавляет X-Admin-Token только к административным вызовам.

Как для 10 лет

Первый экран — витрина, второй — электронный чек, который сам обновляется, третий — пульт кладовщика. Angular меняет только нужные кусочки страницы, не перезагружая весь сайт.

Код: маршруты, витрина, заказ, админка.

Контрольный вопрос: зачем polling на странице заказа?

Выдача асинхронна: HTTP создания уже завершён, worker продолжает работу. Периодический GET показывает пользователю новые статусы и останавливается на терминальном состоянии.

11. Восстановление после ошибок

Профессионально

Администратор видит заказы out_of_stock и delivery_failed. После пополнения пула endpoint retry в транзакции блокирует заказ, проверяет recoverable state, возвращает существующую delivery job в pending и сохраняет стабильные provider request IDs. Повторное нажатие не создаёт вторую job благодаря unique order relation.

Demo reset разрешён только при отсутствии processing jobs. Он удаляет изменяемые demo-данные в порядке зависимостей и воспроизводит seed. Это административная операция, защищённая токеном, а не публичный endpoint.

Как для 10 лет

Если билеты закончились, заказ кладут на полку «нужна помощь». Кладовщик добавляет билеты и снова запускает ту же карточку задания. Новую покупку не создают — продолжают старую с прежними номерами.

Код: retryDelivery(), resetDemo(), управление из Angular.

Контрольный вопрос: почему retry переиспользует provider request ID?

Предыдущий вызов мог завершиться выдачей без ответа. Новый ID выглядел бы для поставщика как новая операция; старый ID возвращает прежний результат.

12. Безопасность, логи, health и метрики

Профессионально

Helmet выставляет защитные HTTP-заголовки. AdminGuard работает fail-closed и сравнивает X-Admin-Token с серверным секретом. Приложение не логирует секретные заголовки; вместо этого структурированные JSON-логи связывают requestId, orderId, eventId и providerRequestId.

/health/live сообщает, что процесс жив; /health/ready дополнительно проверяет БД. Metrics endpoint отдаёт счётчики дублей, outcomes, retries/timeouts и gauges длины очередей. Они отвечают на вопрос «что происходит», а история статусов — «что произошло с конкретным заказом».

Как для 10 лет

Токен — ключ от служебной комнаты. Логи — дневник событий с номерами заказов. Health — лампочки «сервер включён» и «база доступна». Метрики — приборная панель: сколько карточек ждёт и сколько раз сеть подвела.

Код: AdminGuard, bootstrap и логи, MetricsService, operations endpoints.

Контрольный вопрос: чем readiness отличается от liveness?

Liveness отвечает, работает ли процесс. Readiness — способен ли он обслуживать трафик, включая доступность зависимостей вроде PostgreSQL.

13. Как тесты доказывают критерии приёмки

Риск Механизм Доказательство

Профессионально

Unit tests проверяют чистые domain rules. Integration/race suite работает с реальным PostgreSQL и запускает параллельные HTTP-запросы, потому что мок базы не воспроизводит locks и unique races. Playwright проверяет систему снаружи как пользователь. CI затем повторяет lint, types, unit, build, race, E2E и Docker build в чистом окружении.

Как для 10 лет

Маленькие тесты проверяют каждое правило отдельно. Гоночные тесты выпускают к одной двери 50 человек сразу. Браузерный робот нажимает настоящие кнопки. Если все три уровня зелёные, мы проверили детали, давку и весь путь целиком.

Код: race-сценарии, Playwright E2E, CI pipeline.

Контрольный вопрос: почему гонки тестируются с настоящим PostgreSQL?

Correctness зависит от реальных транзакций, lock semantics и UNIQUE. In-memory mock обычно выполняет операции последовательно и может дать ложное чувство безопасности.

14. От исходников до production

git push→CI→Docker image по SHA→migrate deploy→health-check→Nginx + HTTPS

Профессионально

Multi-stage Dockerfile сначала собирает workspace, затем переносит production dependencies, dist, Prisma schema и Angular assets в минимальный runtime. В production Compose API также раздаёт Angular с одного origin; наружу публикуется только localhost port приложения, а PostgreSQL/providers остаются во внутренней сети.

Ручной deploy workflow использует immutable image digest/SHA, выполняет миграции до переключения трафика и проверяет readiness. Secrets хранятся на сервере, не в Git. Nginx завершает TLS и проксирует поддомен к локальному контейнеру.

Как для 10 лет

Docker собирает подписанную коробку приложения. Робот сначала проверяет коробку, сервер готовит таблицы, а потом включает новую версию. Nginx стоит у входа как охранник: принимает безопасные HTTPS-письма и передаёт их приложению.

Код: Dockerfile, production Compose, deploy workflow.

Контрольный вопрос: зачем image привязывается к SHA?

Тег вроде latest может начать указывать на другой образ. SHA однозначно связывает production-бинарник с проверенным commit и делает rollback воспроизводимым.

17. Короткий словарь

Идемпотентность
Повтор одной операции не создаёт новый бизнес-результат.
Инвариант
Правило, которое остаётся истинным при любых допустимых действиях.
Inbox
Таблица для надёжного приёма внешних событий до их обработки.
Lease
Временное право worker обрабатывать job; истекает после сбоя.
Race condition
Ошибка, результат которой зависит от порядка параллельных действий.
Row lock
Временная блокировка строки БД внутри транзакции.
Snapshot цены
Цена и валюта, зафиксированные в момент создания заказа.
Fulfillment
Факт успешной выдачи цифрового кода конкретному заказу.
Backoff
Пауза перед следующим повтором после временной ошибки.
DTO
Явная форма данных, разрешённых на границе API.
